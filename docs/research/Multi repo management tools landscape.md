# Fleet health is unclaimed ground GutCheck can own

No tool found in the research combines a per-repo health verdict, local-only operation and a reviewable fix flow for a folder of personal repos, and that combination is GutCheck's position. Existing tools split into four camps. Runners (gita, mani, myrepos, meta) fan out `git status` and show dirty/ahead/behind at best. Batch-change tools (multi-gitter, git-xargs) open PRs from a script the user writes. Cleanup tools (git-trim, BFG, filter-repo) fix one problem in one repo. Governance tools (Scorecard, Allstar, Safe Settings, Port, Cortex) score or enforce policy but assume an organisation, an installed GitHub App or a SaaS account. Community feedback is thin on dashboards (six 2025-26 Show HN launches drew 1-5 points each) but loud on one pain: dependency-bot noise (one HN thread hit 647 points). Evidence favours a few concrete additions over new surface area: a declarative baseline with drift reporting, release and tooling-version health, safer dependency-automation audits, notifications on change, and PR-based delivery of fixes. Evidence on demand is mostly qualitative, and several GitHub-side claims in the notes are marked unverified; this report flags them.

## Runners and cleanup tools report state, never health

The multi-repo runners are a thin layer. gita is the clearest, showing a colour-coded branch state and dirty symbols per registered repo, but it is a status table and users ask only for ahead/behind counts and a terse mode, each with one reaction ([gita](https://github.com/nosarthur/gita); [#205](https://github.com/nosarthur/gita/issues/205)). mani auto-discovers `.git` folders and runs commands in parallel ([mani](https://github.com/alajmo/mani)). myrepos' site lists its latest release as July 2018, and meta's latest release is April 2021 with an open "still maintained?" issue ([myrepos](https://myrepos.branchable.com/); [meta #314](https://github.com/mateodelnorte/meta/issues/314)). None of these has a dry-run or preview model. GitKraken is the only GUI with a multi-repo concept, but its docs show batch fetch/pull and a cross-repo PR view tied to cloud workspaces, and no health indicators ([GitKraken docs](https://help.gitkraken.com/gitkraken-desktop/workspaces/)). GitHub Desktop and lazygit are single-repo; GitHub Desktop's top issues are a Linux build (4,853 reactions) and multiple windows (228), not a dashboard ([#1525](https://github.com/desktop/desktop/issues/1525); [#3606](https://github.com/desktop/desktop/issues/3606)).

Cleanup tools are narrower still. git-trim detects squash merges and supports `--dry-run`, but has had no release since December 2022 and an open bug where dry-run attempts to push ([git-trim](https://github.com/foriequal0/git-trim); [#206](https://github.com/foriequal0/git-trim/issues/206)). git-sweep is abandoned, BFG and filter-repo rewrite history and so need a force-push ([BFG](https://github.com/rtyley/bfg-repo-cleaner)). The one git-native fleet mechanism, `git maintenance` with `for-each-repo`, optimises object stores and documents no health report ([git-maintenance](https://git-scm.com/docs/git-maintenance)). The notes' own reading is that nobody computes findings such as "no CI", "stale PR" or "unpushed branch with no upstream" across a folder. GutCheck already covers all of those, so its core is validated as differentiated rather than as a gap to fill. The useful lessons from these tools are baseline expectations: JSON output (requested in mani #99 and multi-gitter #441), group filtering, and a visible maintenance story ([mani #99](https://github.com/alajmo/mani/issues/99); [multi-gitter #441](https://github.com/lindell/multi-gitter/issues/441)).

## Governance tools need an organisation that solo developers lack

Scorecard is the healthy, read-only scorer with 19 checks and a risk-weighted aggregate, but its own README warns that the aggregate hides specifics and shifts as heuristics change, and it never fixes anything ([ossf/scorecard](https://github.com/ossf/scorecard)). Repolinter was archived in February 2026 ([repolinter](https://github.com/todogroup/repolinter)). The enforcers are Allstar, Safe Settings and probot/settings. Allstar's hosted instance is retired, so users must run their own GitHub App ([ossf/allstar](https://github.com/ossf/allstar)). Safe Settings is the most capable, with central YAML and dry-run checks on PRs, but runs as a webhook service, cron job or Action ([safe-settings](https://github.com/github/safe-settings)). probot/settings carries a warning that it escalates anyone with push access to admin, and has had an open request for ruleset support since 2023 ([repository-settings/app](https://github.com/repository-settings/app); [#732](https://github.com/repository-settings/app/issues)). Org rulesets and custom properties require an organisation; plan gating is described inconsistently by GitHub's own pages ([org rulesets doc](https://docs.github.com/en/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization)). Developer portals (Port, Cortex, OpsLevel, Soundcheck) are seat-priced products for platform teams. The notes conclude that portals are overbuilt for 10-50 personal repos.

The inference that matters: a developer with twenty personal repos has no policy tool at all. A local baseline file (required files, settings, workflows, per-repo exemptions) checked by GutCheck's existing collectors would fill that hole. The drift half is cheap because GutCheck already stores history. Reverting stays out of scope under its rules; plan, preview, apply covers it. Scorecard's own tracker supports the framing: users asked for a managed per-org App rather than an Action in every repo ([ossf/scorecard #4333](https://github.com/ossf/scorecard/issues)). The notes did not retrieve demand numbers for Safe Settings or Allstar, so the case rests on absence of a local alternative rather than measured demand.

## Dependency noise is the loudest complaint, and cooldowns are the new answer

The strongest community signal is about dependency bots. Filippo Valsorda's "Turn Dependabot off" argued that false-positive alerts "reduce security by causing alert fatigue", and the HN thread reached 647 points and 185 comments ([words.filippo.io](https://words.filippo.io/dependabot/); [HN](https://news.ycombinator.com/item?id=47094192)). Commenters recommend Renovate for grouping and ecosystem coverage, while others merge Dependabot PRs "relentlessly" or auto-merge non-major updates when tests pass. One Ask HN poster reported 20-30 Dependabot PRs a week across their repos, 5-10 hours a week of review, and auto-merging patches that "missed a few important security fixes" ([Ask HN](https://news.ycombinator.com/item?id=45997568)). A July 2026 Show HN, PRoctr, exists purely to triage bot PRs across platforms ([HN](https://news.ycombinator.com/item?id=49109246)). Cooldowns are the 2025-26 theme: Dependabot's `cooldown` delays version updates but not security updates, and a commenter calls its implementation brain-dead ([Schneider](https://christian-schneider.net/blog/dependency-cooldowns-supply-chain-defense); [comment](https://news.ycombinator.com/item?id=47095192)). Renovate's `minimumReleaseAge` has gaps for transitive dependencies and lockfile maintenance ([discussion 38115](https://github.com/renovatebot/renovate/discussions/38115)). A GitGuardian write-up reports an upgrade-to-merge in about 16 minutes during the Shai-Hulud worm, a figure not independently verified ([GitGuardian](https://dev.to/gitguardian/renovate-dependabot-the-new-malware-delivery-system-4g8c)).

GutCheck already flags superseded Dependabot PRs, alerts with fixed versions and Actions security, and it ships a Dependabot template. That makes the cheapest high-signal additions audits of configuration rather than new merge actors: a Dependabot file without `cooldown:` or grouping, and an auto-merge workflow that is not gated to patch/minor and required CI. The auto-merge pattern (`pull_request_target`, `fetch-metadata`, `gh pr merge --auto`) is already in GutCheck's Actions-security territory ([DEV guide](https://dev.to/hidev1977/automatically-merge-dependabot-patch-updates-with-github-actions-316g)). Reachability is the unmet half of Valsorda's argument (he recommends govulncheck); GutCheck cannot run repo code, so a note on relevance in its alert findings is the realistic scope. The notes are balanced on one point: automerge has no consensus and works only with strong CI, so GutCheck should audit and advise rather than merge.

## Local-first, no opaque scores and no tokens are trust points

The Show HN record is a warning on adoption: Repo Linked (Electron, macOS only), Git-Scope, Gitwig and RepoFlock drew 1-3 points and almost no comments ([HN 45678928](https://news.ycombinator.com/item?id=45678928); [HN 49475771](https://news.ycombinator.com/item?id=49475771)). The only substantive critique was of shouldiuse.dev, where users objected to being asked for a GitHub PAT even for public repos and noted that Scorecard-style heuristics can be "wrong (at best) or maliciously gamed (at worst)" ([HN 44399666](https://news.ycombinator.com/item?id=44399666)). Scorecard criticism is consistent: false positives that recur after dismissal in systemd, checks that do not fit single-maintainer projects without Actions, and a view of it as unpaid work pushed on maintainers ([systemd#25042](https://github.com/systemd/systemd/issues/25042); [comment](https://news.ycombinator.com/item?id=44350218); [comment](https://news.ycombinator.com/item?id=45606076)). OpenSSF's own response was maintainer annotations to correct scores ([OpenSSF blog](https://openssf.org/blog/2024/03/05/openssf-scorecard-evaluating-and-improving-the-health-of-critical-oss-projects/)). The lesson for GutCheck is that every finding needs a per-repo, persistent "accepted, don't flag" mechanism, and that per-finding evidence beats an aggregate number. Secret scanning shows the same: GitHub push protection blocks placeholder values in `.env.example` and a configured exclusion did not stop it ([discussion 210435](https://github.com/orgs/community/discussions/210435)). GutCheck's clutter and secrets checks should treat example files as a known false-alarm class.

GitHub's own repository dashboard (December 2025) is a second signal. Users asked for custom repo lists, an ignore option and org/team filters, and the view only counts activity within one year, so old stale repos disappear ([discussion 181683](https://github.com/orgs/community/discussions/181683)). That is direct evidence of an unmet need that GutCheck's folder scan serves, with the ignore list as the thing to copy. On AI agents, the evidence is about instruction-file upkeep: a May 2026 Ask HN found people split on whether CLAUDE.md/AGENTS.md rules are followed at all ([HN 48160604](https://news.ycombinator.com/item?id=48160604)). A preprint reportedly found smells in 100 popular repos' agent files (lint leakage 62%, context bloat 42%), but this is secondary and unverified ([arxiv 2606.15828](https://arxiv.org/html/2606.15828)). GutCheck's agent-setup checks are therefore in a young but real niche; the notes found no primary thread on agent clutter, so that claim stays unsupported.

## Release, drift and notification gaps are cheap and mostly unserved

The gap analysis rates several additions that need no new network or trust model. Release health (commits since the last tag, tag versus `package.json` mismatch, changelog missing the latest tag) is computable from git alone, and release-please, changesets and semantic-release act per repo, so no multi-repo view was found; the notes rate it high value and low effort but retrieved no demand data. Tooling-version drift (`.nvmrc`, `engines`, `go.mod`, workflow `node-version`, EOL runtimes) and duplicated workflow files across repos are reasoned candidates with no sources behind them, so treat their value as inference. Scheduled scans with a notification only on new regressions address a real absence: the local dashboards found (git-scope, gv, CodeBoard, p-mon) are terminal tools, and gitbar is the one menubar app with notification-like behaviour ([gitbar](https://pypi.org/project/gitbar/); [git-scope](https://pkg.go.dev/github.com/echaouchna/git-scope)). Stale-bot criticism (Django, Gutenberg, Drew DeVault) argues for reporting staleness and never auto-closing ([DeVault](https://hacktivis.me/git/mirror/drewdevault.com.git/file/content/blog/stalebot.md.html); [Django list](https://groups.google.com/g/django-developers/c/RAGuVJhT_3M/m/i2h1k-U-AAAJ)). A cross-repo list of issues awaiting a reply fits that, and matches a standing GitHub request for a unified cross-repo PR view ([discussion 34709](https://github.com/orgs/community/discussions/34709)).

Delivery is the largest design question. multi-gitter and git-xargs show that the review step people trust is a PR: dry-run, then branch and PR, with signed commits the top ask (multi-gitter #261 with 8 reactions, git-xargs #93 with 14) ([multi-gitter](https://github.com/lindell/multi-gitter); [git-xargs](https://github.com/gruntwork-io/git-xargs)). git-xargs stages every new and modified file, a footgun GutCheck's "run exactly the planned steps" rule already avoids. Neither tool knows what needs fixing; GutCheck does. Fork and abandoned-repo findings are plausible and cheap (`gh repo sync` exists per fork, and Scorecard's Maintained check uses 90 days) but the notes found no stale-fork tool and no demand evidence ([GitHub docs](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork)). Licence checks via the SPDX SBOM endpoint will return many NOASSERTION entries, so the notes advise flagging only copyleft dependencies in permissive repos and a missing LICENSE; GutCheck already has the latter ([SBOM docs](https://docs.github.com/en/rest/dependency-graph/sboms)). Actions cost is least attractive: per-repo billing needs new usage endpoints with unconfirmed token scope, and 2026 pricing changed repeatedly ([GitHub changelog](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/)).

## Conclusion

The landscape suggests GutCheck has been solving the right problem for an audience that has no good tool and does not post about it: community evidence is sparse because solo developers script around the gap, and dashboard launches that ignore trust (tokens, closed source, single scores) get ignored. The competition is therefore less other health tools than the pull of Renovate's configurability and the bar set by Scorecard's false-positive complaints. Winning means being the tool whose findings can be dismissed with a reason, whose evidence is visible, and whose fixes arrive as a previewed plan.

The sharpest opportunity is where the community's loudest pain meets GutCheck's existing strengths: dependency-bot noise combined with Actions-security knowledge. Auditing cooldown and auto-merge configuration, and shipping them in templates, addresses a documented 2025-26 supply-chain concern without GutCheck ever merging a PR. What remains uncertain is demand: no reaction counts, Reddit threads or user research on personal-repo audits were obtained, and several GitHub plan and pricing details are unverified. The first two recommendations are cheap enough to test that demand before committing to baselines or PR delivery.
