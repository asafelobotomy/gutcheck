# GitHub repository settings, security and supply-chain checks a multi-repo health checker could automate (as of Nov 2026)

Scope note: GutCheck already covers (per docs/sources.md): classic protection or active ruleset on default branch, SHA pinning, top-level `permissions:`, script injection (limited field list), pull_request_target/workflow_run + PR-head checkout, self-hosted on public repos, Dependabot config/grouping/cooldown/auto-merge, secret scanning/push protection/CodeQL default/PVR/Dependabot security updates, SECURITY.md, CODEOWNERS/issue templates/topics (info), license, release tag vs manifest. "Deliberately not checked": signed commits/releases, SBOM, Webhooks, CII badge, fuzzing. Candidates below are NEW or clear refinements. Research caveat: several 2026 items come from search snippets or third-party write-ups; each is marked where only a secondary source was read.

## 1. Rulesets vs classic branch protection; tag protection; required checks, signed commits, linear history, merge queue

### Takeaway
Rulesets are GitHub's current mechanism (layered, targetable at branches AND tags, with bypass lists and many more rule types than classic protection). The 2026 Trivy action tag-rewrite incident makes "version tags are unprotected" a concrete, cheap-to-detect gap. GutCheck currently checks only the default branch; extending to tag rules, and to the *content* of rules (not just "something exists"), is the main opportunity.

### Cited Findings
- Endpoints: `GET /repos/{o}/{r}/rulesets` (supports `includes_parents`, `targets`), `GET /repos/{o}/{r}/rulesets/{id}`, and `GET /repos/{o}/{r}/rules/branches/{branch}` which returns the *effective active* rules for a branch including org-level rules; rules in "evaluate"/"disabled" rulesets are excluded. `bypass_actors` appears only for users with write access to the ruleset. `evaluate` mode is Enterprise-only. — [REST: rules](https://docs.github.com/en/rest/repos/rules)
- Rule catalogue (usable as check targets): restrict creations/updates/deletions, block force pushes, require linear history (needs squash or rebase merge allowed), require signed commits, require PR (approvals 0-10, dismiss stale approvals, approve most recent push, require code-owner review, require conversation resolution, allowed merge methods), required status checks (can pin to a specific GitHub App as source), required deployments, require secret scanning alerts resolved (public preview), require code scanning results, code quality results, license compliance results, code coverage (preview), restrict file paths/extensions/size/path length. Page does not cover merge queue, "workflows" rule or Copilot review rule. — [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- Trivy compromise (March 2026): attacker force-pushed 76 of 77 `trivy-action` tags; the only surviving tag was protected by immutable releases. Recommended: tag rulesets with no updates/deletions/force pushes (optionally restrict tag creation to release automation), immutable releases, create releases as drafts then publish, avoid PATs for release automation (prefer GITHUB_TOKEN, then GitHub App, then fine-grained PAT with expiry). Tag rulesets work immediately without waiting for immutable releases. — [Eclipse Foundation blog](https://blogs.eclipse.org/post/mika%C3%ABl-barbero/dont-become-next-trivy-how-make-your-releases-tags-and-automation-resistant) (single secondary source for the incident details)
- Scorecard Branch-Protection is High risk and looks at default and release branches (force push, deletion, unreviewed or unchecked merges); Code-Review (High) checks recent changes were human-reviewed. — [Scorecard checks](https://raw.githubusercontent.com/ossf/scorecard/main/docs/checks.md)

### Candidate checks (what / how / fix / risk)
1. **Tag protection missing for release tags.** Detect: repo has tags matching `v*`/semver (local `git tag`) or releases, AND `GET /repos/{o}/{r}/rulesets?targets=tag` (plus `includes_parents=true`) shows no active tag ruleset with `deletion` + `non_fast_forward` (+ `update`) rules matching `refs/tags/v*`. Fix: plan to create a tag ruleset via `POST /repos/{o}/{r}/rulesets` (`target: tag`, include `refs/tags/v*`, rules `deletion`, `non_fast_forward`, `update`). Risk: low (additive; may block the owner's own re-tagging, so preview wording matters; leave `bypass_actors` for repo admin). Severity suggestion: info (private/solo) warn (public with releases/Actions consumers).
2. **Rule-content depth for default branch** (refinement of existing check): use `GET /repos/{o}/{r}/rules/branches/{default}` and report which of `non_fast_forward`, `deletion`, `pull_request`, `required_status_checks`, `required_linear_history`, `required_signatures` are present. Report "protected but no required status checks while CI exists", "requires PR with 0 approvals" as info. Fix: ruleset update/create. Risk: low-medium (can lock out a solo maintainer; keep admin bypass).
3. **Ruleset in evaluate/disabled mode only** — `GET /repos/{o}/{r}/rulesets` entries with `enforcement != active`; info: "ruleset exists but is not enforcing". Fix: `PUT` enforcement=active. Risk: low.
4. **Bypass list too broad** — ruleset `bypass_actors` with `actor_type: RepositoryRole`, `bypass_mode: always` for broad roles (write). Info. Source: [REST: rules](https://docs.github.com/en/rest/repos/rules).
5. **Signed-commits drift** (currently "deliberately not checked"): optional opt-in. Detect `required_signatures` rule vs local `git log --format=%G?` proportion (note GutCheck disables `log.showSignature`/gpg programs; use GitHub's `verification` field via API instead, not local gpg). Keep as opt-in info only.
6. **Required status check names that no longer exist** (stale required checks block merges forever): compare ruleset `required_status_checks[].context` against job names/`name:` in `.github/workflows/*.yml`. Detect purely locally + one API call. Fix: edit ruleset. Risk: low. (Inference; no authoritative doc states this as a standard check.)
7. **Merge queue**: no authoritative source read this session for a merge-queue rule type; treat as out of scope (single-user workspace, queue is team-oriented).

### Inferences
- Tag-ruleset check is the highest-value addition: cheap (one list call), directly addresses the March 2026 tag-rewrite class of attack, and the fix is additive.
- Because GutCheck already skips private repos on free plans (403), the same 403 handling should apply to tag rulesets.
- "Classic vs rulesets" recommendation: GitHub docs treat rulesets as the superset; I did not find a doc page in this session that says classic protection is deprecated, so do not flag classic protection as a defect, only offer ruleset-based fixes.

### Gaps
- Merge queue and the `workflows` ("required workflows") rule type: not covered by the fetched page; not verified.
- Whether GitHub officially "recommends" rulesets over classic protection in current docs: not confirmed by a fetched statement.

## 2. GitHub Actions hardening beyond what GutCheck does

### Takeaway
Big 2026 platform shifts: `pull_request_target` blocked by default on public repos from 2 Dec 2026 (brownouts 9 and 16 Nov), `actions/checkout` v7 refuses fork checkout in privileged triggers, Node 20 removed (23 Sep 2026), and workflow dependency lockfiles (`actions.lock`) launched Oct 2026. GutCheck can add: checkout version staleness, `persist-credentials`, artifact/cache poisoning patterns, workflow-level `sha_pinning_required` setting, trusted-publishing/OIDC suggestions, and a broader script-injection context list modelled on zizmor.

### Cited Findings
- `GET/PUT /repos/{o}/{r}/actions/permissions` returns `enabled`, `allowed_actions` (all/local_only/selected) and `sha_pinning_required`; `.../permissions/workflow` returns `default_workflow_permissions` (read|write) and `can_approve_pull_request_reviews`; `.../permissions/fork-pr-contributor-approval` returns `approval_policy` (`first_time_contributors_new_to_github`, `first_time_contributors`, `all_external_contributors`); `.../permissions/access` applies to private repos only. Classic tokens need `repo` scope. — [REST: Actions permissions](https://docs.github.com/en/rest/actions/permissions)
- SHA pinning enforcement setting (Aug 2025): an allowed-actions policy option that makes workflows fail if an action is not pinned to a full SHA; enforced at run time (PRs with unpinned actions still merge), checks composite actions too, no exclusion list. — [GitHub changelog 2025-08-15](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/); behaviour details from [Zenn write-up (Japanese, secondary)](https://zenn.dev/shunsuke_suzuki/articles/github-actions-enforce-sha-pinning)
- pull_request_target blocked by default in PUBLIC repos from 2 Dec 2026 unless an Actions event policy allows it (Free, Team, Enterprise Cloud; not GHES); starts in evaluate mode; brownouts 9 and 16 Nov 2026 16:00-18:00 UTC; earlier date was 2 Nov. No API for reading policies mentioned. — [GitHub changelog 2026-11-02](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2)
- Per Wiz: `actions/checkout@v7.0.0` (18 Jun 2026) blocks fork code checkout by default in `pull_request_target` and PR-triggered `workflow_run`; backported 20 Jul to v2.8.0, v3.7.0, v4.4.0, v5.1.0, v6.1.0 (mutable tags inherit it, SHA pins to older versions do NOT). Still exploitable: SHA-pinned old checkout, `git clone`/`gh pr checkout` bypass, `issue_comment`/`repository_dispatch` triggers, script injection, artifact poisoning (`pull_request` uploads, privileged `workflow_run` downloads and runs), non-ephemeral self-hosted runners, `allow-unsafe-pr-checkout: true`. Wiz detection advice: grep for risky triggers, `allow-unsafe-pr-checkout`, `download-artifact` in workflow_run, direct git/gh checkout, and resolve SHA-pinned checkout refs to tags. — [Wiz: Pwn Request Reckoning](https://www.wiz.io/blog/github-actions-security-pwn-request-reckoning) (vendor blog; dates from a single source, partly corroborated by the GitHub changelog above)
- Workflow dependency lockfiles: `gh extension install github/gh-actions-lock`, `gh actions-lock` writes the lockfile after scanning `.github/workflows/`; each `uses` pinned to a commit SHA; a "Require lockfile" policy exists; if an allowlist is used, tag-pinned entries stop matching after onboarding. — [Docs: lock workflow dependencies](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies). Public preview 14 Oct 2026 (file `.github/workflows/actions.lock` per a third-party summary; one source claims GA 28 Oct, not confirmed on github.blog) — [changelog](https://github.blog/changelog/2026-10-14-github-actions-workflow-lockfiles-in-public-preview/), [InfoQ](https://infoq.com/news/2026/11/github-actions-lockfiles-ga)
- 2026 roadmap (published 26 Mar 2026, all items then "planned"): dependency locking, workflow execution policies (event/actor rules, evaluate mode), scoped secrets, native egress firewall for hosted runners, immutable-actions "hardened publishing" with no date. — [GitHub blog roadmap](https://github.blog/news-insights/product-news/whats-coming-to-our-github-actions-2026-security-roadmap/)
- zizmor audit catalogue (use as the blueprint for local checks): `artipacked` (git credentials persisted by checkout leak via artifacts; lower severity on checkout v6+), `cache-poisoning`, `template-injection`, `unpinned-uses`, `excessive-permissions`, `dangerous-triggers` (now also `issue_comment`), `self-hosted-runner` (pedantic), `github-env` (writes to GITHUB_ENV/GITHUB_PATH), `secrets-inherit`, `impostor-commit`, `ref-confusion`, `obfuscation`, `forbidden-uses`, `bot-conditions` (spoofable `github.actor` checks for dependabot), `known-vulnerable-actions` (GitHub advisories), `superfluous-actions`, `ref-version-mismatch` (version comment vs SHA), `stale-action-refs` (SHA not on a tag), `archived-uses`, `insecure-commands` (`ACTIONS_ALLOW_UNSECURE_COMMANDS`), `concurrency-limits` (pedantic), `use-trusted-publishing`, `unpinned-images`, `unsound-condition`. — [zizmor audits](https://docs.zizmor.sh/audits/)
- Scorecard: Dangerous-Workflow is Critical; Token-Permissions High; Pinned-Dependencies Medium; Webhooks Critical (webhook without secret); Signed-Releases High; SBOM Medium; Packaging Medium; SAST Medium; Binary-Artifacts High; Maintained High. — [Scorecard checks](https://raw.githubusercontent.com/ossf/scorecard/main/docs/checks.md)
- Release workflow hardening advice: pin SHAs, minimum GITHUB_TOKEN permissions, prefer GitHub-hosted runners, lint with zizmor and poutine, treat Dependabot action bumps as security reviews (red flags: same-tag digest change, SHA older than tag, new unfamiliar action), use OIDC for cloud/registry access. — [Eclipse blog](https://blogs.eclipse.org/post/mika%C3%ABl-barbero/dont-become-next-trivy-how-make-your-releases-tags-and-automation-resistant)

### Candidate checks (what / how / fix / risk)
1. **`persist-credentials` not false** (artipacked). Detect: workflow step `uses: actions/checkout@...` with no `with: persist-credentials: false`, in workflows that also `upload-artifact` (higher) or run later steps with third-party actions. Local YAML only. Fix: add `with:\n  persist-credentials: false` (exact text edit, previewable). Risk: low; breaks only workflows that later `git push` using the checkout credential (skip/downgrade when `git push|git commit|gh pr` appears in the job). Info; warn when upload-artifact is in the same job. Source: [zizmor artipacked](https://docs.zizmor.sh/audits/).
2. **Old or privileged-checkout misuse**: `actions/checkout` pinned to a SHA/tag older than the 2026 hardening backports, in a workflow with `pull_request_target`/`workflow_run`/`issue_comment`; and `allow-unsafe-pr-checkout: true` (error). Direct `git clone`/`gh pr checkout` in privileged-trigger workflows (error). Local only; needs a small table of patched versions and a tag-to-SHA resolution (gh API `GET /repos/actions/checkout/git/ref/tags/<tag>`) or just compare the `# vX.Y.Z` comment. Source: Wiz above. Risk: none (report only), fix is advisory. Refine existing "privileged triggers" check: also include `issue_comment` and `repository_dispatch`.
3. **Artifact poisoning pattern**: `workflow_run` workflow containing `download-artifact` / `dawidd6/action-download-artifact` followed by executing the content (`bash`, `source`, `node`, `npm`), or reading `github.event.workflow_run.head_branch/head_sha` in `run:`. Local. Error if fork-triggered `pull_request` is the source. Source: Wiz.
4. **Cache poisoning**: `actions/cache` (or setup-* `cache:`) used in a workflow triggered by `release`/tag push/`publish` that also publishes (npm publish, docker push, `gh release`), or cache writes in privileged triggers. Local. Fix: remove cache in release jobs or use `restore-keys`-less read-only (`actions/cache/restore`). Warn. Source: [zizmor cache-poisoning](https://docs.zizmor.sh/audits/).
5. **Broader template-injection contexts**: extend the field list beyond body/title/ref/label/message/name/email/page_name/default_branch to `github.event.pull_request.head.label`, `head.repo.default_branch`, `github.event.commits[*].author.name`, `github.event.review.body`, `github.event.workflow_run.head_branch`, `head_commit.message`, `github.head_ref`; plus `github-script` `script:` inputs and composite-action `run:`. Fix: move into `env:` and reference `"$VAR"`. Source: zizmor `template-injection`; [Secure use](https://docs.github.com/en/actions/reference/security/secure-use). Risk: low.
6. **`github-env`**: `>> $GITHUB_ENV` or `>> $GITHUB_PATH` where the written value derives from `${{ }}`/untrusted step output. Warn. Source: zizmor.
7. **`secrets: inherit`** on reusable-workflow calls: info/warn. Fix: list the secrets explicitly. Source: zizmor; roadmap mentions "scoped secrets/reusable workflow secret inheritance" as a platform change.
8. **Spoofable bot conditions**: `if: github.actor == 'dependabot[bot]'` (auto-merge guards) rather than `github.event.pull_request.user.login`; ties into GutCheck's existing auto-merge warning. Warn. Source: zizmor `bot-conditions`.
9. **Version comment mismatch / stale SHA**: `uses: owner/repo@<sha> # v1.2.3` where comment missing (pedantic) or tag does not resolve to that SHA (`gh api repos/owner/repo/git/ref/tags/v1.2.3`; annotated tags need a second deref). Also SHA not on any tag (`stale-action-refs`) and impostor commits (SHA exists only in a fork network: `gh api repos/owner/repo/commits/<sha>` then `.../branches-where-head` is not stable, so only flag when the commit is not reachable from the repo, via `GET /repos/{o}/{r}/compare/HEAD...<sha>` status `diverged`/404; unverified approach). Warn; info for missing comment. Source: zizmor.
10. **Archived or known-vulnerable actions**: for each pinned action repo, `GET /repos/{owner}/{repo}` -> `archived: true`; `GET /advisories?affects=<owner>/<repo>&ecosystem=actions` for known vulnerable versions (e.g. tj-actions/changed-files CVE-2025-30066). Network-light (cache per action across workspace). Warn. Source: zizmor `archived-uses`, `known-vulnerable-actions`.
11. **Actions policy at repo level** (read-only API): `sha_pinning_required=false` while workflows exist -> info "enable SHA pinning enforcement" (fix: `PUT .../actions/permissions` with `sha_pinning_required: true`; risk medium: breaks any unpinned or composite-nested action at run time); `default_workflow_permissions=write` -> warn (fix `PUT .../permissions/workflow` `default_workflow_permissions=read`; risk low-medium, workflows lacking `permissions:` that push/comment will break, so only offer after a `permissions:` block exists in every workflow); `can_approve_pull_request_reviews=true` -> warn (lets Actions approve PRs, defeats review rules; fix set false, low risk); `allowed_actions=all` info; fork-PR approval policy weaker than `all_external_contributors` on public repos -> info. Source: [REST: Actions permissions](https://docs.github.com/en/rest/actions/permissions).
12. **Lockfile readiness**: info that `.github/workflows/actions.lock` absent when workflows use third-party actions; fix `gh actions-lock` (plan step, writes a file; preview the diff). Mark "preview feature, plan eligibility unclear" and make opt-in. Source: lockfile docs above. Risk: medium (once onboarded every dependency needs an entry; local `./` actions need `$/` migration flags).
13. **pull_request_target readiness for 2 Dec 2026**: public repos with any `pull_request_target` workflow -> warn "blocked by default from 2 Dec 2026 unless an event policy allows it"; fix advice: switch to `pull_request`, or add explicit event policy (no REST API confirmed for reading/setting policies, so advice only). Time-limited; remove after December. Source: GitHub changelog 2026-11-02.
14. **OIDC / trusted publishing**: workflows that `npm publish`, `twine upload`, `cargo publish`, `gem push`, or use `aws-actions/configure-aws-credentials`/`google-github-actions/auth` with `secrets.*_TOKEN|KEY|ACCESS_KEY` and no `id-token: write`. Info. Fix: advice (trusted publishing on npm/PyPI/crates.io/RubyGems; `role-to-assume` for AWS). Source: Eclipse blog (OIDC for cloud/registries), zizmor `use-trusted-publishing`. Risk: advice-only.
15. **Long-lived PATs in release automation**: `secrets.*PAT*`/`GH_TOKEN: ${{ secrets.… }}` used with `gh release`/push. Info; suggest GITHUB_TOKEN or GitHub App. Source: Eclipse blog.
16. **`permissions: write-all` or missing at job level with `id-token`/`contents: write` on PR-triggered jobs**: extension of existing token-permissions check (job-level granularity; `pull_request` + write perms). Existing coverage partially; refine.
17. **Unpinned docker images in workflows/containers**: `container:`/`services:`/`docker://` image by tag rather than digest — zizmor `unpinned-images`; GutCheck's pinning check already passes digest-pinned images, so extend to flag tag-only. Info.
18. **`ACTIONS_ALLOW_UNSECURE_COMMANDS`** set anywhere (error). Source: zizmor `insecure-commands`. Also `set-output`/`save-state` (deprecated) and `::set-env`: see section 6.

### Inferences
- A single Node-based local "mini-zizmor" (YAML parse already exists in scanner) covering items 1-9 would match the community standard without needing to shell out to zizmor; alternatively, detect `zizmor`/`actionlint` in CI config and report their absence (info) — GutCheck's rule "never run a repo's code" is compatible with running the user's own installed zizmor offline against the files, but that is a design choice, not from a source.
- Item 2 matters because GutCheck's pinning advice (pin to SHA) can pin users to a *pre-hardening* checkout; when suggesting pins the planner should choose a SHA of a patched release.
- Item 13 is perishable (deadline 2 Dec 2026).

### Gaps
- No REST endpoint found for reading Actions event/actor policies or the "Require lockfile" policy (changelog says Insights only).
- Exact lockfile path/plan availability: docs page did not state; third-party summary gives `.github/workflows/actions.lock`; GA date (28 Oct) is only in InfoQ.
- zizmor severities not published on the fetched page; page was truncated at ~100k of 131k characters (`undocumented-permissions`, `unpinned-uses` details not read).
- StepSecurity harden-runner and actionlint were not researched in detail (budget); no verified claims about them here.
- Immutable (action) releases for *actions*: roadmap lists it with no date; nothing to detect yet.

## 3. OpenSSF Scorecard, Best Practices, SLSA, attestations, SBOM, immutable releases, signing

### Takeaway
Scorecard has 20 checks; most are replicable locally. GutCheck covers about half (Branch-Protection, Dangerous-Workflow, Token-Permissions, Pinned-Dependencies, Dependency-Update-Tool, License, Security-Policy, SAST-ish via CodeQL). Not covered: Binary-Artifacts, Webhooks, Signed-Releases, SBOM, Packaging, Maintained, Fuzzing, CI-Tests (partly), Vulnerabilities (OSV). Immutable releases (GA 28 Oct 2025) and release attestations are the notable new supply-chain controls.

### Cited Findings
- Full Scorecard list: Binary-Artifacts, Branch-Protection, CI-Tests, CII-Best-Practices, Code-Review, Contributors, Dangerous-Workflow, Dependency-Update-Tool, Fuzzing, License, Maintained, Packaging, Pinned-Dependencies, SAST, SBOM, Security-Policy, Signed-Releases, Token-Permissions, Vulnerabilities, Webhooks (risks: Critical for Dangerous-Workflow and Webhooks; High for Binary-Artifacts, Branch-Protection, Code-Review, Dependency-Update-Tool, Maintained, Signed-Releases, Token-Permissions, Vulnerabilities). — [Scorecard checks](https://raw.githubusercontent.com/ossf/scorecard/main/docs/checks.md)
- Scorecard definitions: Signed-Releases = release assets include signature files, SLSA provenance earns top score; SBOM = SBOM in source or as release artifact; Binary-Artifacts = compiled executables committed; Maintained = recent commits and issue activity or archived; Vulnerabilities = OSV open unfixed vulns. — same source
- Immutable releases GA 28 Oct 2025 (preview 26 Aug 2025): tag locked to commit and cannot be moved/deleted while release exists; assets cannot be changed or deleted; a signed release attestation is created; tags can't be reused even after repo deletion/recreation; title, notes, prerelease flag remain editable. Enabled per repo or org. Docs fetched do not mention a REST API to read the setting. Releases published before enabling do not gain attestations. Verification `gh release verify <tag>` / `gh release verify-asset <tag> <asset>`. — [Immutable releases GA](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/), [docs](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [preview](https://github.blog/changelog/2025-08-26-releases-now-support-immutability-in-public-preview/)
- Provenance attestations via `actions/attest` with `id-token: write`, `contents: read`, `attestations: write`; verify with `gh attestation verify`; reusable-workflow build+attest is said to meet SLSA v1.2 Build L3; SBOMs where feasible. — [Eclipse blog](https://blogs.eclipse.org/post/mika%C3%ABl-barbero/dont-become-next-trivy-how-make-your-releases-tags-and-automation-resistant)

### Candidate checks (what / how / fix / risk)
1. **Binary-Artifacts**: tracked files with executable magic (ELF `7f45 4c46`, PE `MZ`, Mach-O, `.jar`, `.class`, `.dll`, `.so`, `.exe`, `.wasm`) via `git ls-files` + first bytes read (GutCheck already reads headers for secrets). Info/warn; ignore known test fixtures and `gradle-wrapper.jar` (Scorecard validates it). Fix: advice (move to releases/LFS/build step); never rewrites history. Source: Scorecard.
2. **Webhooks without secret** (currently "deliberately not checked"): `GET /repos/{o}/{r}/hooks` (needs admin) -> `config.secret` is masked `********` when set; absent when unset; also `config.insecure_ssl == "1"`. Critical per Scorecard, but only affects repos with webhooks; one extra call per administered repo. Fix: owner sets secret in UI (API PATCH would need the secret value, which GutCheck must not handle: advice only). Source: Scorecard Webhooks; API field behaviour from my background knowledge (not verified this session).
3. **Signed-Releases / provenance for repos that publish releases**: `GET /repos/{o}/{r}/releases` assets lacking `*.sig`, `*.asc`, `*.sigstore(.json)`, `*.intoto.jsonl`, `*.pem`, `*.minisig`, `*.bundle`; workflow lacking `actions/attest*`/`slsa-framework/slsa-github-generator`/`sigstore/cosign-installer`. Info, only when releases have binary assets (not source-only). Fix: add `actions/attest` step (plan edits a workflow; preview). Source: Scorecard; Eclipse blog. Reconsider the "Deliberately not checked" entry for signed releases: now cheap and standardised.
4. **Immutable releases not enabled** on repos that publish releases/tags consumed by others. Detect: no API confirmed. Option: infer from `GET /repos/{o}/{r}/releases` field `immutable` (I believe releases expose an `immutable` boolean; NOT verified this session) and flag releases with `immutable:false`. Fix: owner enables Settings > General > Releases (advice only until an API is confirmed). Info. Source: GitHub changelog GA.
5. **SBOM**: release assets or repo files named `*.spdx(.json)`, `*.cdx.json`, `bom.json`, `sbom.*`; or workflow with `anchore/sbom-action`, `cyclonedx`, `syft`, `actions/attest-sbom`. Info only for repos that publish releases (matches Scorecard). Fix: advice/workflow snippet. Dependency Graph SBOM export exists (`GET /repos/{o}/{r}/dependency-graph/sbom`; background knowledge, unverified here).
6. **Maintained / archived-but-still-active**: `archived:true` repos with local uncommitted work or open Actions schedules; and conversely repos with no commit in >90 days plus open Dependabot alerts. Local `git log` + `GET /repos` `archived`/`pushed_at`. Info. Source: Scorecard Maintained.
7. **Vulnerabilities**: open Dependabot alerts count/severity: `GET /repos/{o}/{r}/dependabot/alerts?state=open&severity=critical,high` (needs `security_events`/admin). GutCheck checks config/enablement but not open alerts. Warn on critical/high. Also open secret-scanning alerts: `GET /repos/{o}/{r}/secret-scanning/alerts?state=open` (report count only, never values) and code-scanning alerts `GET /repos/{o}/{r}/code-scanning/alerts?state=open`. Fix: advice/open URL; Dependabot PRs. Source: Scorecard Vulnerabilities; endpoints from background knowledge (unverified this session) - confirm against docs.github.com/rest before building.
8. **CI-Tests / SAST**: already partially covered (tests check, CodeQL). Refinement: SAST also satisfied by Semgrep/SonarCloud/`github/codeql-action` in a workflow even when default setup is off.
9. **Best Practices badge**: stays "not checked" (low value); optional info if README lacks badge. Fix none.

## 6. Actions cost/minutes hygiene

### Takeaway
All detectable locally from workflow YAML; main authoritative anchors are the 60-day scheduled-workflow rule and the Node 20 removal/`ubuntu-latest` move. Several runner-image dates came from third-party trackers.

### Cited Findings
- "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days"; schedules run only on the default branch; may be delayed at the start of every hour. — [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). (The page did not state the 360-minute default timeout.)
- Node 20 is no longer available in Actions: Node 24 default migration (official date edited to 16 Jun 2026; one source says 2 Jun), Node 20 removal 23 Sep 2026; the `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION` opt-out is gone; third-party actions still on Node 20 may fail; first-party actions updated to Node 24. — [GitHub changelog 2026-09-23](https://github.blog/changelog/2026-09-23-node-20-is-no-longer-available-in-github-actions), earlier notice [2026-01-12](https://github.blog/changelog/2026-01-12-deprecation-of-node-20-on-github-actions-runners/)
- macOS 13 runner image retired 4 Dec 2025. — [GitHub changelog 2025-09-19](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down/). Upcoming image migrations (May 2026 notice, not read in detail): [changelog 2026-05-14](https://github.blog/changelog/2026-05-14-github-actions-upcoming-image-migrations). Third-party trackers: ubuntu-22.04 supported to 17 Apr 2027, macOS 14 EOL 2 Nov 2026, `ubuntu-latest` moving to Ubuntu 26.04 (announced 17 Sep 2026 per one write-up) — [endoflife.date](https://www.endoflife.date/github-actions-runner-images) (secondary; verify against actions/runner-images)
- zizmor `concurrency-limits` (pedantic), `superfluous-actions`, `archived-uses`. — [zizmor audits](https://docs.zizmor.sh/audits/)

### Candidate checks (what / how / fix / risk)
1. **Missing `timeout-minutes`** on jobs (default 360 min per GitHub's workflow syntax docs, not re-verified here): local YAML; info; fix insert `timeout-minutes: 15` (or 30) per job after preview; risk low-medium (long builds killed; use 2x the median of recent run durations from `gh run list --json` if available).
2. **Missing `concurrency`** with `cancel-in-progress: true` on `pull_request`/`push` CI workflows (never on deploy/release workflows). Info. Fix template: `concurrency:\n  group: ${{ github.workflow }}-${{ github.ref }}\n  cancel-in-progress: true`. Risk low for CI; wrong for publish jobs, so skip workflows with release/publish/deploy steps.
3. **Cron on inactive public repo**: workflow has `schedule:` and default-branch last commit >50 days ago (public repos) -> warn "will be disabled at 60 days"; if `GET /repos/{o}/{r}/actions/workflows` shows `state: disabled_inactivity` -> warn already disabled. Fix: `gh workflow enable <id>` (re-enable is reversible; ask), or push a commit/keepalive. Source: events docs above. (`disabled_inactivity` state value is from background knowledge, unverified.)
4. **Cron on high-load minute**: `cron: '0 * * * *'` or `0 0 * * *` -> info, use off-peak minute. Source: events docs (delays at start of every hour).
5. **Removed/EOL runner labels**: `runs-on:` containing `ubuntu-20.04` (retired in 2025; background knowledge), `macos-13` (retired 4 Dec 2025), `macos-12`, `windows-2019` (background knowledge), `ubuntu-18.04`; warn since jobs queue forever/fail. Also flag `*-latest` info is unnecessary. Maintain a small table in code with dates. Fix: replace label (preview). Risk low-medium (toolchain differences). Upcoming: macOS 14 (2 Nov 2026 per third-party tracker) - mark "verify".
6. **Deprecated action majors on Node 16/20**: pinned action versions known to run on `node16`/`node20`. Detect by reading the action's `action.yml` `runs.using` via `GET /repos/{o}/{r}/contents/action.yml?ref=<sha>` (works with the pinned SHA, cacheable per SHA) -> `node12|node16|node20` = warn; fix: bump to the first release using `node24` (Dependabot does this if configured). Also common offenders: `actions/checkout@v3/v4`, `setup-node@v3`, `upload-artifact@v3` (v3 artifact API shut down; background knowledge). Source: Node 20 changelog above.
7. **Deprecated workflow commands**: `::set-output`, `::save-state`, `::set-env`, `::add-path` in `run:` -> warn; fix: write to `$GITHUB_OUTPUT`/`$GITHUB_STATE`/`$GITHUB_ENV`/`$GITHUB_PATH` (exact rewrite). `set-env`/`add-path` are disabled by default (`ACTIONS_ALLOW_UNSECURE_COMMANDS`, zizmor `insecure-commands`). Source: [zizmor](https://docs.zizmor.sh/audits/); deprecation of `set-output` from background knowledge.
8. **Cache usage**: `GET /repos/{o}/{r}/actions/cache/usage` (active_caches_size_in_bytes; default repo limit 10 GB, evicts LRU; background knowledge) -> info when near limit; stale caches deletable via `gh cache delete` (low risk, regenerates). Also artifact retention: `upload-artifact` without `retention-days` (default 90) in big-artifact repos: info.
9. **Duplicate/redundant workflow triggers**: both `push` and `pull_request` on same branches with no `concurrency` (double runs): info. Local.
10. **Superfluous actions**: actions replicating preinstalled tools (e.g. wrapping `gh`, `git`, `docker` commands) - zizmor `superfluous-actions`: info, advice only.
11. **Workflows never run / always failing**: `gh run list --workflow` last 20 conclusions; all `failure` for >30 days -> warn (burning minutes). Uses existing gh CI status data.

### Inferences
- Items 1, 2, 5, 7 are exact, deterministic text edits that fit the plan/preview/apply model well and give the "minutes hygiene" story concrete value.
- A small dated table of retired runner labels and Node-runtime-by-action-SHA cache is the main maintenance burden; sourcing it from `actions/runner-images` releases is better than hardcoding third-party dates.

### Gaps
- Official default `timeout-minutes` (360) statement not found on the fetched page.
- Official retirement dates for ubuntu-20.04, windows-2019, windows-2022, ubuntu-22.04 and macOS 14 not confirmed from github.blog in this session; the May 2026 "upcoming image migrations" post was not opened.
- Cache limit figures and `disabled_inactivity` value not verified.
- harden-runner, actionlint, OpenSSF Best Practices criteria, SLSA.dev: not fetched (tool-call budget).
