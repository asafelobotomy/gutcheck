# Close the config-hook hole, then widen GutCheck's coverage

GutCheck has one security gap to fix before it adds any feature: since Git 2.54, a repo's own config can define hooks (`hook.<name>.event` plus `hook.<name>.command`), and GutCheck's `core.hooksPath=/dev/null` and `core.fsmonitor=false` settings do not stop them. The coordinator reproduced this on git 2.56.0, where a config hook fired on `git commit` under READONLY_GIT settings. Passing `-c hook.<name>.enabled=false` blocked it, and GutCheck's action-time hook detection (`repoHooks` in `src/git-safety.js`) looks only at hook files, so config hooks are neither blocked nor reported. After that fix, the research favours checks that reuse machinery GutCheck already has. The biggest sets are workflow-YAML checks modelled on zizmor and Scorecard, runtime end-of-life checks from version pins, lockfile and manifest drift, and "unfinished git state" markers. The perishable item is `pull_request_target` on public repos, which GitHub blocks by default from 2 December 2026. Larger features (an OSV vulnerability scan, a rescue-bundle action, a workspace manifest, an opt-in integrity check) are valuable but add network use, new state or new write paths. Several 2026 platform dates and API field names rest on secondary sources or on the researchers' memory; section five lists them so nothing is hard-coded unchecked.

## Security fix first: repo-defined hooks run despite the current git hardening

Git 2.54 (April 2026) added config-defined hooks: `[hook "<name>"]` with `event` and `command`, a `hook.<name>.enabled=false` switch, and `git hook list <event>`. Git 2.55 added `hook.<name>.parallel` and `hook.jobs` ([Highlights 2.54](https://github.blog/open-source/git/highlights-from-git-2-54/), [Highlights 2.55](https://github.blog/open-source/git/highlights-from-git-2-55/)). Because the definition lives in the repo's own `.git/config`, a cloned or tampered repo can carry a hook that `core.hooksPath` never sees. The researchers flagged this exact gap but did not test it. The coordinator then confirmed it directly on this machine with a throwaway repo. The config entries `hook.evil.command` and `hook.evil.event=pre-commit` created a marker file during `git commit` even with `-c core.hooksPath=/dev/null -c core.fsmonitor=false`, and adding `-c hook.evil.enabled=false` blocked it (coordinator reproduction on git 2.56.0). Read-only scans rarely trigger hooks, so the main exposure is GutCheck's write actions. `commit-all`, pull and merge, checkout, push (the `pre-push` event) and anything that updates a ref (the `reference-transaction` event) can all reach a config hook.

The fix fits where GutCheck already works. `src/git-drivers.js` reads the repo's own config entries to blank filter and diff drivers before each scan or plan git call, so the same layer can enumerate every `hook.<name>.*` key in the repo's local config and add a `-c hook.<name>.enabled=false` override for each. The coordinator found `hook.<name>.command=` and `hook.<name>.event=` also blocked execution, which makes blanking all three keys a sensible belt-and-braces choice. Two related pieces belong in the same change. First, `repoHooks` in `git-safety.js` should report config hooks (via `git config --local --get-regexp '^hook\.'` or `git hook list <event>`) and surface them in the plan preview, not just hook files. Second, the same enumeration should cover hooks in included config files and in the global config, because `includeIf` targets (`gitdir:`, `onbranch:`, `hasconfig:remote.*.url:`) can pull in more definitions ([git-config](https://git-scm.com/docs/git-config)). A regression test in the style of the existing accuracy tests should build a temp repo with a marker-creating config hook and assert that every GutCheck git entry point (scan, plan, apply) leaves no marker. The risk is low: the override only disables hooks the user did not define through GutCheck, though users who rely on config hooks for their own pre-commit checks will see them skipped during GutCheck writes, which the preview should say.

## Quick wins: deterministic checks that extend code GutCheck already has

The best quick wins share a profile: they parse files GutCheck already reads, produce exact text edits that suit plan, preview and apply, and rarely fire false alarms. Ranked by value, the first is the **perishable `pull_request_target` readiness warning**. GitHub will block `pull_request_target` by default on public repos from 2 December 2026 unless an Actions event policy allows it, with brownouts on 9 and 16 November 2026 ([GitHub changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2)). GutCheck already finds these workflows. It only needs a public-repo warning with advice to move to `pull_request` or add an explicit policy. No REST endpoint for policies was found, so the fix is advice only, and the check can be deleted after December. Wiz adds that `actions/checkout@v7` (18 June 2026) refuses fork checkouts in privileged triggers, and that the fix was backported to mutable tags but not to older SHA pins ([Wiz](https://www.wiz.io/blog/github-actions-security-pwn-request-reckoning), a vendor blog and a single source for the dates). That has a direct consequence for GutCheck's own advice: when its planner suggests pinning to a SHA, it should pick a patched release, or it pins users to a pre-hardening checkout.

Second is a **mini-zizmor for workflow YAML**, using [zizmor's published audit catalogue](https://docs.zizmor.sh/audits/) as the blueprint. The cheapest members are `persist-credentials` not set to false (`artipacked`, fix is a two-line `with:` edit, downgraded when the job later pushes), widening the script-injection field list to contexts such as `github.head_ref`, `workflow_run.head_branch` and `head_commit.message`, `secrets: inherit`, spoofable `github.actor == 'dependabot[bot]'` conditions (which ties into GutCheck's auto-merge warning), `ACTIONS_ALLOW_UNSECURE_COMMANDS`, and writes to `$GITHUB_ENV` of untrusted values. Third is **runner and runtime staleness in workflows**. GitHub removed Node 20 from Actions on 23 September 2026 ([changelog](https://github.blog/changelog/2026-09-23-node-20-is-no-longer-available-in-github-actions)), so actions whose `action.yml` still says `runs.using: node20` can fail. Detection reads `action.yml` at the pinned SHA via the contents API and caches per SHA. Retired runner labels (`macos-13` was retired 4 December 2025, per [GitHub changelog](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down/)) and missing `timeout-minutes` or `concurrency` round out the "minutes hygiene" story as exact edits. The caveat is that the dated label table should come from `actions/runner-images`, not third-party trackers.

Fourth is the **end-of-life check from version pins**, which the ecosystem notes rank as the best value-for-effort item in the whole set. GutCheck currently says only "no runtime pin". It could compare `.nvmrc`, `engines.node`, `requires-python`, `go.mod` and CI matrix values with a bundled table, optionally refreshed from the [endoflife.date v1 API](https://endoflife.date/api/v1/products/nodejs/). The data are surprising today: Node 25 reached end of life on 2026-06-01, and Python 3.10 reached end of life on 2026-10-01 ([Python devguide](https://devguide.python.org/versions/)). Go supports only 1.27 and 1.26 ([Go release policy](https://go.dev/doc/devel/release)). Node moves to one major per year from 27, so next-LTS logic must be data-driven ([Node.js blog](https://nodejs.org/blog/announcements/evolving-the-nodejs-release-schedule)). A subtlety matters for false alarms: a `go.mod` `go` line is a minimum, not the version in use ([Go toolchain docs](https://go.dev/doc/toolchain)), and a lower-bound range is a "pinned floor", so the finding should label which source it used and report only when the sole CI version is end-of-life. Fifth is **unfinished git operations and detached HEAD**: marker files (`rebase-merge/`, `rebase-apply/`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`) are the canonical signal from [git-prompt.sh](https://raw.githubusercontent.com/git/git/master/contrib/completion/git-prompt.sh), they are read-only to detect, and the only sensible fix is a preview of `--abort`, never automatic, because abort discards conflict resolutions. Reading paths through `git rev-parse --git-path` keeps this correct for worktrees and reftable repos.

The identity check must stay workspace-level and quiet, because it is a heuristic with no prevalence data behind it beyond blog anecdotes.

## Larger features: higher value, but new network use, state or write paths

The largest single addition is a **dependency vulnerability layer from lockfiles through OSV**. GutCheck verifies that Dependabot and scanning are switched on but never reads what they found. OSV.dev offers one no-authentication batch endpoint across npm, PyPI, crates.io, Go and Maven, and the docs state no rate limits ([OSV API](https://google.github.io/osv.dev/api/)). Parsing lockfiles and sending name and version triples runs no repo code, which keeps it inside the scan rules. The costs are real. Dependency names leave the machine, so it must be opt-in and exclude private, git and path dependencies, and results need dev versus prod classification to avoid noise. A cheaper first step for repos GutCheck can already reach with `gh` is counting open Dependabot, secret-scanning and code-scanning alerts by severity (counts only, never secret values). The endpoints for these come from the researchers' memory and need confirming against docs.github.com before building, and the alert endpoints need admin or security-event scope.

Second is a **rescue-bundle action for work that exists only locally**. The community evidence is strongest here: account loss and unpushed work drive a steady stream of backup scripts ([Lupine.dev](https://lupine.dev/articles/github-takeout/), [Addy Osmani](https://addyosmani.com/blog/backing-up-a-github-account/)), yet a plain `git bundle` misses stashes, untracked files and config ([simplified.guide](https://www.simplified.guide/git/bundle-create-restore), [gitolite tips](https://gitolite.com/tips-3.html)). The gitolite recipe, `git bundle create --all --not --remotes` plus stash patches and an untracked-file list, maps neatly onto plan, preview and apply, writes only to a user-chosen folder and can be verified with `git bundle verify`. A dry run that lists "what exists only locally" (unpushed commits, stashes, untracked files, repos with no remote) is useful on its own and is the natural first release. Third is a **workspace manifest with a restore command**, borrowed from mani, ghq and gita, so a new machine can clone everything missing and GutCheck can report "on GitHub but not cloned" and the reverse ([gita](https://pypi.org/project/gita/0.16.3), [gickup](https://github.com/cooperspencer/gickup)). The star counts quoted in the community notes (gita 1,962, mani 789) show a persistent but modest demand, and no breakout winner exists, so this is a differentiator, not a necessity.

Fourth are the **opt-in deep checks**, consistent with how `tests-run` is already opt-in. An integrity action running `git fsck --connectivity-only --no-dangling`, `git commit-graph verify` and `git refs verify` stays out of default scans for speed, which `docs/sources.md` already justifies ([git-fsck](https://git-scm.com/docs/git-fsck)). LFS pointer detection (a worktree file under 1024 bytes starting with the LFS version line, per the [LFS spec](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md)) and `git ls-files --eol` mixed or CRLF findings both read files directly. Both should route through `ctx.safeGit`, because it was not confirmed that `ls-files --eol` ignores `filter=` drivers and `git lfs fsck` can move files into `.git/lfs/bad` ([git-lfs-fsck](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-fsck.adoc)). The `--renormalize` fix produces a large noisy commit and rewrites blame, so it must stay a preview with a clear warning. Fifth is **agent-debris cleanup**, backed by many reported problems with stale or orphaned agent worktrees in Claude Code issues ([#26725](https://github.com/anthropics/claude-code/issues/26725), [#31488](https://github.com/anthropics/claude-code/issues/31488)) and by a vivid incident in which a loop of `git worktree remove --force` deleted about 29 worktrees with uncommitted work ([Mergify](https://mergify.com/blog/the-day-my-ai-agent-deleted-29-git-worktrees)). The lesson for GutCheck's design is to classify each worktree (clean and merged, versus dirty or locked with a live PID), act per worktree, and refuse `--force` on dirty ones. That matches GutCheck's "never delete work" posture better than any generic prune.

## How the recommendations fit GutCheck's rules, and what to skip

Nearly everything above stays inside GutCheck's rules because detection is file parsing, `git` reads or a fixed-URL GET, and fixes are previewed edits or printed commands. The recurring pressure points are three. First, anything that touches history stays out: `git lfs migrate import`, mailmap rewrites and `--renormalize` are preview-and-advice only, since GutCheck never rewrites history. Second, project-executing commands (`./gradlew wrapper`, `./gradlew clean`, `govulncheck`, `pre-commit autoupdate`, `docker compose`) can appear only as printed steps, never in a scan, because they run repo code. Third, new network calls (OSV, endoflife.date, registry deprecation lookups, `git ls-remote` for stale pre-commit tags) need an opt-in and must send no repo contents. The README-visible test rule, no network in `npm test`, means the end-of-life table should ship bundled with an "as of" date and treat the live refresh as optional.

Several ideas are better skipped or deferred. Typosquat detection has a high false-positive rate and no authoritative source. Dependency-licence conflict analysis edges into legal advice. Webhooks-without-secret, signed releases and SBOM were deliberately excluded because they suit large open-source projects, and the notes make a fair case to revisit them only for repos that publish release assets. Even then they are info-level. A weaker check, merge-queue detection, has no source at all and suits teams, not a single-user workspace. Finally, the notes' proposed scoring history and a "dependency dashboard" view of all bot PRs are product ideas borrowed from Renovate and Cortex. They rest on vendor documentation and anecdote, not independent evidence, so they belong after the checks above.

## Which claims rest on secondary or unverified sources

The evidence quality is uneven, and these items should be re-verified before any rule ships. Several 2026 platform facts came from third-party or single sources: the Trivy tag-rewrite incident details (Eclipse Foundation blog only), the `actions/checkout@v7` dates and backport list (Wiz only, partly corroborated by GitHub's changelog), the lockfile feature's file name `.github/workflows/actions.lock` and a 28 October GA date (a third-party summary and InfoQ, not on github.blog), and runner-image retirement dates such as macOS 14 on 2 November 2026 (endoflife.date, a secondary tracker). The Node 24 default date varies by source (2 June versus 16 June 2026); the GitHub changelog should be treated as authoritative. Several API details are from the researchers' memory, not fetched pages: webhook `config.secret` masking, the `immutable` field on releases, the dependabot, secret-scanning and code-scanning alert endpoints, the dependency-graph SBOM endpoint, `disabled_inactivity` workflow state, CODEOWNERS errors endpoint behaviour (only third-party mirrors read), and OSV's request schema. The git configuration recommendations (`fetch.prune`, `rerere.enabled`, `transfer.fsckObjects` and similar) came from a fetch tool answering from general knowledge on a truncated page, so cite each key against git-config when implementing. Likewise the git-sizer per-asterisk thresholds came from an LLM-summarised source file and should be spot-checked. The exact git release that introduced `maintenance is-needed`, the geometric task and `git refs optimize` was never confirmed, which argues for version-gating on `git --version`. Security-research figures about malicious agent skills (98,380 scanned, 157 confirmed malicious) and CVE numbers for MCP issues were not checked at their primary source ([CSA note](https://labs.cloudsecurityalliance.org/research/csa-research-note-skill-md-agent-context-poisoning-20260506), [Mondoo](https://mondoo.com/blog/agent-skills-real-power-real-risk)). Finally, the community evidence is thin. Reddit, Lobsters and Stack Overflow were unreachable, so demand is inferred from tool star counts and blog posts, not upvotes. The config-hook finding in the first section is the exception: it was reproduced on this machine, not taken from a source.

## Conclusion

The central lesson is that GutCheck's most important gap is a hardening gap, not a feature gap. Its safety promise (scans and actions never run repo code) was written against file-based hooks, and Git 2.54 moved hook definition into the same config file GutCheck already reads for drivers. That suggests a standing practice: whenever Git gains a new way to execute configured commands, the blanking layer in `git-drivers.js` and the reporting in `git-safety.js` need a matching update, with a test that builds a marker-creating repo. The research also shows that GutCheck can change how it is used for little cost. A few parse-only checks (EOL pins, workflow hygiene, lockfile drift, unfinished git operations) would turn it from a "is anything wrong" reporter into one that catches problems the platforms are about to enforce, such as the 2 December `pull_request_target` change and the Node 20 removal.

The larger features share a theme: they all turn what GutCheck already knows into something recoverable or actionable, whether that is a rescue bundle for local-only work, a vulnerability list in place of an "enabled" flag, or a manifest that restores a workspace. They are worth doing in that order of confidence, each behind an opt-in. The unresolved questions are practical: whether config-hook enumeration should also cover the global and system config, how many of the memory-sourced API fields hold up against current docs, and whether the personal-workspace audience wants scorecard-style history at all.
